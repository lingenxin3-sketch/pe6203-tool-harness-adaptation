# 不制作 PPT 的项目演示方式

先说明：项目解决的是“工具升级后，AI 的工具知识如何更新”。展示三种策略在同一个任务、同一个工具版本上的记录，让老师能够追到原始证据。

## 一、回放真实实验记录

在项目目录运行：

```powershell
.venv/Scripts/python.exe scripts/demo_evidence.py --task 28 --version iter3
```

这是**已保存的真实实验回放，不是现场重新推理**。界面会明确标注。它显示三种策略分别改写了哪些说明、实际调用了哪些工具、哪里报错、生成了哪些文件，以及已经完成的本地模型评分。未评分时不会编造分数。

任务 28 的中间版本适合解释“为什么不必把所有说明都改一遍”：这组工具的契约没有变化，全量重写仍改写了三条说明，之后的运行未能创建任务文件。选择性方法保留这些说明，实际创建了文件。但任务内容仍有事实性问题，展示时应同时说明，不能只展示优点。

之后打开对应 `result.json` 和实际生成的 `tasks.md`，让老师看到界面摘要确实来自原始记录。其他案例可以更换 `--task` 和 `--version`；正式结论应以完整结果表为准。

再运行下面的命令展示“旧参数为什么不够用”：

```powershell
.venv/Scripts/python.exe scripts/demo_evidence.py --task 113 --version iter5
```

此案例中，旧知识没有新要求的优先级和标签参数，反复调用失败；局部修补后能够保存五条待办。打开实际 `workspace/tasks.json` 可以验证。这些任务还未完成、未获批准，不能说仪表盘已经实现。

## 二、需要现场运行时

按 `REPRODUCTION.md` 的开发运行步骤执行。该步骤使用开发任务，不更改正式实验。先确认本地模型已就绪，且没有其他正式任务占用它。现场推理需要时间，不要承诺固定几秒完成。

## 三、六个人各讲一个关键问题

1. 如何证明这是真的 AI 调用真实工具，而不只是聊天回答？
2. 工具名字、参数和说明分别有哪些变化？
3. 局部修补如何确定哪些知识需要更新，为什么要考虑相关工具？
4. 三种策略如何保持公平，哪些任务属于恢复、哪些属于保持？
5. 分数如何计算，模型评分和实际文件不一致时怎么处理？
6. 哪些失败来自漏更新或过度更新，哪些来自模型本身或缺失资源？

## 四、10 分钟怎么讲

| 时间 | 负责人 | 展示内容 |
|---|---|---|
| 0:00—1:30 | 1 | 解释企业工具升级问题，说明真实模型、真实工具和本地运行方式 |
| 1:30—3:00 | 2 | 展示参数或工具变化前后差别；说明三个环境版本 |
| 3:00—4:30 | 3 | 解释只更新相关说明的方法，以及依赖扩展对照为什么没有证明有效 |
| 4:30—6:00 | 4 | 展示公平配置、18 个固定任务、TF/PE/ECS 结果与单次实验局限 |
| 6:00—8:00 | 5 | 回放任务 113，指出任务文件与评分之间的分歧；解释约 65% 的更新 token 节省 |
| 8:00—10:00 | 6 | 回放任务 28 的失败要点，总结适用条件、限制和复现证据 |

后续 5 分钟问答由对应负责人回答，其余成员补充证据。提前打开报告、结果图和两段回放，避免把全部时间花在现场等待模型推理上。回放必须明确说是已保存的真实实验记录。

结论用一句直白的话表达：局部修补省了更新工作，但没有保证每次任务都做得更好；我们用真实文件和调用记录检查了分数是否可信。不要把本地模型打分说成老师会给的课程分数。目前不制作幻灯片。
